# タネシステム設計

> 状態: v1実装済み。意味判定モデルとevent editor支援は後続  
> 対象: Pygameランタイム、KSイベント、日記、セーブ、イベント解禁  
> 対象外: 自由記述の意味判定アルゴリズムそのもの。ここでは判定器との接続契約だけを定義する。

## 1. 目的

タネは、会話イベント中に得た人物の謎を解くための手掛かりである。

- タネ同士は親子関係を持ち、全体として循環のない有向グラフ（DAG）を構成する。
- タネに指定された会話内テキストは、水色かつ下線付きで表示する。
- そのテキストをクリックすると、補足の会話を一時的に挿入する。
- クリックの有無にかかわらず、実際にタネが出現したイベントを最後まで完了すると取得する。
- 取得したタネは、その日の終わりに日記へ追記する。
- ターニングポイントでは、取得済みタネを確認しながら自由記述で推理を入力する。
- 推理の成否に応じて、以後のイベントの解禁・停止状態を変更する。

## 2. 用語

| 用語 | 意味 |
|---|---|
| タネ定義 | ID、本文、親、日記上の配置など、制作側が用意する不変データ |
| 取得 | イベント完了時に、そのタネをプレイヤーの恒久状態へ記録すること |
| 出現 | 親条件を満たしたタネ付きテキストが、実際の会話ステップで表示されること |
| 注釈閲覧 | 水色テキストをクリックして補足会話を見ること。取得条件ではない |
| 未日記化 | 取得済みだが、まだその日の終わりの日記へ追記されていない状態 |
| ターニングポイント | 自由記述の推理を行い、成功・失敗の物語分岐を確定する地点 |

## 3. 基本方針

### 3.1 静的データと進行状態を分離する

- タネの文章、親子関係、日記上の場所は `data/seed_catalog.json` に固定する。
- ターニングポイントの区分名と結果分岐は `data/turning_points.json` に固定し、同じ情報を二重管理しない。
- プレイヤーが取得した事実だけを `data/current_state/seed_state.json` に保存する。
- 子一覧は親一覧からロード時に逆算し、二重管理しない。
- 日記の並び順を取得順から作らない。全解禁時のページと枠を先に決める。

これにより、途中でタネが増えても既存セーブの並び順が崩れず、後から取得したタネが不自然な位置へ追記されることを防ぐ。

### 3.2 親子関係はDAGとする

- 自己参照は禁止する。
- A→B→Aのような循環は禁止する。
- 親が複数ある場合は、既定で全親取得を出現条件とする。
- 別ルート対応が必要なタネだけ `parent_mode: "any"` を指定できる。
- `parent_mode` を省略した場合は `"all"` とする。

同一イベント内で初取得するタネ同士を親子にしてはならない。親の取得確定はイベント終了時だからである。静的検証でエラーにする。

イベントの出現順序は既存のイベント解禁・停止で制御する。タネの親子関係からイベントの起動可否を逆算してはならない。

### 3.3 イベント全体ではなく通過ステップを記録する

KSファイルに記述されていても、未選択の分岐にあるタネは取得しない。

1. タネ付き会話ステップが表示される。
2. 親条件を満たしていれば、そのIDを当該イベントの `encountered_seed_ids` に追加する。
3. イベントを正常完了した時だけ、一覧を取得済み状態へ移す。
4. メニュー復帰、強制終了、ロードなどでイベントを中断した場合は確定しない。

イベント途中セーブへ対応する場合は、`dialogue_state.json` に `encountered_seed_ids` も保存し、再開時に復元する。

## 4. タネの状態遷移

```text
親条件未達
  └─ unavailable

親条件達成
  └─ eligible
       └─ タネ付きステップ表示
            └─ encountered_pending
                 ├─ イベント中断 → eligibleへ戻る
                 └─ イベント正常完了 → acquired_unjournaled
                                            └─ 一日の終わり
                                                 → acquired_journaled
```

注釈をクリックしたかどうかは、この状態遷移に入れない。`annotation_opened` は必要なら実績・演出用の補助情報として別に記録するが、ストーリー条件には使わない。

すでに取得済みのタネが再登場した場合は、水色・下線と注釈クリックを維持するが、重複取得や日記への再追記はしない。

## 5. 静的データ

### 5.1 `data/seed_catalog.json`

```json
{
  "schema_version": 1,
  "characters": [
    {
      "id": "NOK",
      "display_name": "乃花",
      "sort_order": 10
    }
  ],
  "seeds": [
    {
      "id": "NOK_TP1_001",
      "character_id": "NOK",
      "turning_point_id": "NOK_TP1",
      "title": "止まった日記",
      "journal_text": "乃花の日記は、ある日を境に途切れている。",
      "parents": [],
      "parent_mode": "all",
      "source_events": ["E120"],
      "journal_location": {
        "page": 1,
        "slot": 1
      }
    },
    {
      "id": "NOK_TP1_002",
      "character_id": "NOK",
      "turning_point_id": "NOK_TP1",
      "title": "同じ日付",
      "journal_text": "日記が止まった日と、あの事件の日付は同じだ。",
      "parents": ["NOK_TP1_001"],
      "source_events": ["E126"],
      "journal_location": {
        "page": 1,
        "slot": 2
      }
    }
  ]
}
```

### 5.2 ID規則

- タネID: `{CHARACTER}_{TURNING_POINT}_{3桁連番}`
- ターニングポイントID: `{CHARACTER}_TP{連番}`
- 一度リリースしたIDは変更・再利用しない。
- 表示順変更は `journal_location` で行い、IDを変えない。

### 5.3 静的検証

起動時または制作ツールの検証コマンドで、次を検査する。

- ID重複
- 存在しない親ID
- 循環参照
- `character_id` と `turning_point_id` の不整合
- `turning_points.json` に存在しないターニングポイントID
- 同一ページ・同一slotの重複
- `source_events` に存在しないイベントID
- KS内の存在しないタネID
- KSで使用されているのに `source_events` に含まれないイベント
- 親と子を同じイベントで初取得する構成
- 対応する注釈ブロックの欠落または重複

## 6. プレイヤー状態

### 6.1 `data/current_state/seed_state.json`

```json
{
  "schema_version": 1,
  "acquired": {
    "NOK_TP1_001": {
      "source_event_id": "E120",
      "acquired_game_date": "1999-06-03",
      "journaled_game_date": "1999-06-03"
    }
  },
  "journal_days": [
    {
      "game_date": "1999-06-03",
      "seed_ids": ["NOK_TP1_001"]
    }
  ],
  "turning_point_results": {
    "NOK_TP1": {
      "result": "correct",
      "attempt_count": 1,
      "resolved_game_date": "1999-06-10",
      "answer_text": "乃花は母親を守るために嘘をついた",
      "judge_version": "seed-judge-v1"
    }
  }
}
```

`answer_text` は主人公が発話した内容の再表示とデバッグに使用する。個人情報を外部送信せず、セーブデータ内だけに保持する。

### 6.2 セーブ対象

`seed_state.json` を次のすべてへ追加する。

- `SaveManager.state_files`
- `data/templates/seed_state_template.json`
- 各セーブスロット
- ニューゲーム時の状態リセット

古いセーブにファイルがない場合は空状態を自動生成し、ロード失敗にはしない。

## 7. KS記述形式

### 7.1 タネ対象テキスト

会話本文の一部を次のインラインタグで囲む。

```ks
//乃花//
「あの日から、[seed id="NOK_TP1_001"]日記は一行も増えていない[/seed]の。」
```

- タグ自体は表示文字数に含めない。
- 表示文字だけを水色・下線にする。
- ルビ・傍点はタネ内に含めてよい。
- タネタグ同士の入れ子は禁止する。
- 同一会話行に複数のタネを置いてよい。

親条件を満たさない状態でイベントが誤って起動した場合、対象文字列そのものは通常色で表示する。ただし「タネとしては出現していない」扱いとし、クリック不可・取得対象外にする。文章自体を消すと会話が不自然になるため、フェイルセーフでは本文を残す。

### 7.2 注釈会話

注釈は対象タネが登場するKSファイル内へ、選択肢と同様の補助ブロックとして記述する。ローダーはブロックを本編の段落列から分離して保持するため、通常進行では再生されない。

```ks
[seed_dialogue id="NOK_TP1_001"]
    //{苗字}//
    「日記が止まった日には、何か意味がありそうだ。」
    //乃花//
    「……そこまで気にすること？」
[/seed_dialogue]
```

- `id` は同じKS内の `[seed id="..."]` と一致させる。
- クリック時だけ軽量な注釈会話スタックへ積む。
- 注釈終了後は、クリック前の会話ステップ、表示済み文字数、背景、立ち絵へ戻る。
- v1の注釈内では会話文だけを許可する。
- 注釈会話はバックログへ「タネ注釈」と分かる印を付けて追加する。

注釈閲覧は何度でも可能とする。イベント取得、日記追記、分岐条件には影響しない。

## 8. 会話画面での操作

### 8.1 表示

- 通常色: 設定値 `SEED_TEXT_COLOR`
- ホバー色: 設定値 `SEED_TEXT_HOVER_COLOR`
- 装飾: 1px以上の下線
- マウスカーソル: リンク用カーソル
- 文字送り途中では、表示済みの文字だけ当たり判定を持つ。
- 折り返しで複数行になった場合は、行ごとの矩形を同じタネIDへ結び付ける。

色の具体値は実画面で決め、コードへ直接埋め込まず `core/config.py` に置く。

### 8.2 入力優先順位

現在行にクリック可能なタネがある場合のマウス入力は、次の順で処理する。

1. タネ文字列のクリック
2. 選択肢クリック
3. 通常の会話送り

タネをクリックした同じ入力で会話を送ってはならない。

キーボードによる注釈選択はv1後のアクセシビリティ対応とする。

## 9. イベント終了時の取得

イベントごとにメモリ上で次を保持する。

```python
EventSeedSession(
    event_id="E120",
    encountered_seed_ids={"NOK_TP1_001"},
)
```

正常終了時に `SeedManager.complete_event()` を一度だけ呼ぶ。

```python
new_ids = seed_manager.complete_event(
    event_id=current_event_id,
    encountered_seed_ids=session.encountered_seed_ids,
    game_date=current_game_date,
)
```

戻り値は今回新規取得したIDだけとする。取得済みIDは含めない。

取得書き込みとイベント完了記録は、遷移前に両方成功させる。将来的には一時ファイル＋置換で原子的に保存し、片方だけ進む状態を避ける。

特殊会話である `HOME_DIARY` や朝の出発会話は、タネタグを含む場合だけ同じ取得処理を使う。通常イベントIDを持たない一時会話からは取得させない。

## 10. 日記

### 10.1 二種類の見せ方

日記には「その日の追記」と「恒久的な人物別ページ」を共存させる。

1. 日別追記
   - その日に新規取得したタネを取得順で表示する。
   - 日付とタネID一覧を `journal_days` に一度だけ記録する。
2. 人物別ロジックツリー
   - キャラクターごとにタブを分ける。
   - キャラクター内をターニングポイントごとに分ける。
   - タネは `journal_location.page/slot` の固定位置へ表示する。

日別追記は「今日何を知ったか」を示し、人物別ページは「謎全体のどこまで分かったか」を示す。

### 10.2 固定配置

- キャラクタータブは、その人物の最初のタネを日記化した時に公開する。
- ターニングポイントページも、その区分の最初のタネを日記化した時に公開する。
- 未取得slotにはタイトルを出さず、空欄または伏せた罫線だけを表示する。
- 取得後は同じslotへ本文を表示する。
- 親子線は、両端のタネが日記化された時だけ描画する。
- 将来のタネ追加は空きslotを使う。公開後のslot移動はセーブ互換性ではなく見た目の互換性を壊すため、原則行わない。

### 10.3 一日の終わり

帰宅後の既存日記開始時に、次を一度だけ行う。

1. `journaled_game_date` が空の取得済みタネを列挙する。
2. 現在日付の `journal_days` に追記する。
3. 人物別固定ページで表示可能にする。
4. `journaled_game_date` を設定して保存する。
5. 今回の追記件数を `HOME_DIARY` の表示へ渡す。

0件なら追記演出を省略して、通常の日記会話へ進む。ロードや帰宅画面への再入場で二重追記されないよう、この処理は冪等にする。

## 11. ターニングポイント

### 11.1 定義

ターニングポイントの表示、自由記述判定、結果分岐の定義を `data/turning_points.json` に置く。

```json
{
  "schema_version": 1,
  "turning_points": [
    {
      "id": "NOK_TP1",
      "character_id": "NOK",
      "title": "前半戦の謎",
      "sort_order": 10,
      "required_seed_ids": ["NOK_TP1_001", "NOK_TP1_002"],
      "attempt_policy": "once",
      "on_correct": {
        "unlock_events": ["E140"],
        "lock_events": ["E141"],
        "set_flags": {"NOK_TP1_RESULT": "correct"}
      },
      "on_incorrect": {
        "unlock_events": ["E141"],
        "lock_events": ["E140"],
        "set_flags": {"NOK_TP1_RESULT": "incorrect"}
      }
    }
  ]
}
```

`required_seed_ids` は画面に並べる想定タネの定義であり、イベントの起動条件ではない。ターニングポイントの起動順はKSの `event_control` で明示する。また「入力文に必ず書く単語」の意味でもない。

### 11.2 画面フロー

```text
ターニングポイントイベント開始
  → 対象人物・区分の日記ページを開く
  → 取得済みロジックツリーを閲覧
  → 自由記述入力
  → 入力内容を主人公の台詞として表示
  → AnswerJudgeへ判定要求
  → correct / incorrect
  → 結果を保存し、結果フラグを設定
  → 成功側または失敗側のKS進行へ戻る
  → 各分岐内のevent_controlで次イベントを明示
```

自由記述UIはIMEを前提とする。

- `TEXTEDITING` と `TEXTINPUT` を使う。
- IME変換中のEnterを送信扱いにしない。
- 送信は画面上の決定ボタン、またはCtrl+Enterとする。
- 最大文字数は設定値とし、初期値は120文字とする。
- 空白だけの入力は送信不可とする。

### 11.3 判定器との接続契約

判定方式を交換できるよう、ランタイム側は次の結果だけに依存する。

```python
AnswerVerdict(
    result="correct",       # correct / borderline / incorrect / error
    confidence=0.84,
    judge_version="seed-judge-v1",
    reason_codes=("required_concepts_met",),
)
```

- `correct` は成功側へ進む。
- `incorrect` は失敗側へ進む。
- `borderline` は再入力または専用の惜しい演出へ進め、物語上は未確定のままにする。
- `error` は失敗判定にせず、再試行可能なシステムエラー表示にする。

同じ回答と同じ `judge_version` からは同じ結果が返る決定的な判定器とする。

### 11.3.1 ローカル意味類似判定

自由記述判定は、同梱した `ruri-v3-30m` INT8 ONNXモデルを使用し、通信せずに実行する。

1. `reject_patterns` に一致する明白な矛盾語は `incorrect`
2. `canonical_answer` または `accepted_answers` の正規化完全一致は `correct`
3. `canonical_answer` / `positive_examples` の最高類似度と `hard_negatives` の最高類似度を比較する
4. `hard_negatives` 側が近い、または誤答類似度が `hard_negative_threshold` 以上なら `incorrect`
5. 正解側類似度が `correct_threshold` 以上で、かつ誤答側との差が `correct_margin` 以上なら `correct`
6. 正解側類似度が `borderline_threshold` 以上でも、誤答側との差が足りなければ `borderline`
7. それ以外は `incorrect`

否定文や主体の取り違えは正解文とも高い類似度になるため、`hard_negatives` はターニングポイントごとに必ず作者が定義する。閾値は実モデルで正解言い換えと類似誤答を計測して決める。

```json
{
  "canonical_answer": "増田は真性包茎である",
  "semantic_judge": {
    "enabled": true,
    "correct_threshold": 0.95,
    "borderline_threshold": 0.90,
    "hard_negative_threshold": 0.994,
    "correct_margin": 0.002,
    "reject_patterns": ["仮性"],
    "positive_examples": ["増田は真性包茎なんだ"],
    "hard_negatives": [
      "増田は真性包茎ではない",
      "増田は仮性包茎である"
    ]
  }
}
```

`borderline` と `error` では回答結果や物語フラグを保存せず、入力画面を閉じない。

### 11.4 結果とイベント解禁

ランタイムは結果を `seed_state.json` へ保存し、`{TP_ID}_RESULT` フラグへ `correct` または `incorrect` を設定する。イベントの解禁・停止は、成功・失敗の各KS分岐に作者が記述した `event_control` だけで行う。タネ依存や `required_seed_ids` からイベント状態を逆算しない。

`attempt_policy` は次を許可する。

| 値 | 動作 |
|---|---|
| `once` | 最初の確定結果を変更しない |
| `retry_until_correct` | 不正解後も再挑戦でき、正解時に成功側へ確定する |
| `repeatable` | 毎回判定する。特殊用途のみ |

既定値は `once` とする。

## 13. 既存フローへの接続順

```text
KSロード
  → タネタグ解析
  → 会話ステップ表示
  → 親条件確認
  → タネ描画・遭遇記録
  → 任意で注釈会話
  → KS正常終了
  → EventProgress.record_completion
  → SeedManager.complete_event
  → 時間進行・画面遷移
  → 夜のHOME_DIARY開始
  → SeedManager.finalize_day
  → 日記会話・自由行動
```

朝のプリロード済み会話への専用遷移は変更しない。タネ取得処理は通常のイベント完了経路へ追加し、朝会話のローディング省略条件を広げない。

## 14. 異常系

| 状況 | 動作 |
|---|---|
| 親未取得で子タネイベントが起動 | 通常文字として表示し、取得しない。警告ログを出す |
| カタログにないタネID | 通常文字として表示し、取得しない。開発時は検証エラー |
| 注釈定義がない | 水色表示は維持するがクリック不可。開発時は検証エラー |
| イベント中断 | 遭遇タネを確定しない |
| 同じイベント完了処理が二度呼ばれる | 取得、日記、分岐適用を重複させない |
| 古いセーブにseed_stateがない | 空状態を生成して継続 |
| 判定モデルのロード失敗 | 不正解にせず、再試行できるエラー表示 |
| カタログに循環がある | 起動時にタネシステムを無効化し、制作時検証は失敗扱い |

## 15. テスト条件

### 15.1 単体テスト

- 複数親 `all` と `any` の出現条件
- 循環検出
- 子一覧の逆算
- 未通過分岐のタネが取得されないこと
- 注釈未クリックでも正常終了時に取得されること
- 注釈クリックだけでは取得されないこと
- 中断時に取得されないこと
- 再実行時に重複取得されないこと
- 同日複数イベントのタネが一つの日別追記へまとまること
- 日記化処理の冪等性
- ターニングポイント結果適用の冪等性
- 古いセーブの自動移行

### 15.2 描画・入力テスト

- タネ文字が水色かつ下線で描画されること
- 折り返したタネの全行をクリックできること
- 未表示文字にクリック判定がないこと
- タネクリックで同時に会話送りされないこと
- 注釈終了後に背景、立ち絵、会話位置が戻ること
- ルビ・傍点を含むタネの当たり判定がずれないこと
- IME変換確定Enterで回答が送信されないこと

### 15.3 結合テスト

1. 親タネイベントを完了する。
2. 夜の日記へ追記される。
3. 親イベント末尾の `event_control` により子タネイベントが解禁される。
4. 子タネ注釈を開かずにイベントを完了する。
5. 子タネが取得され、翌日記の固定slotへ入る。
6. 第3イベント末尾の `event_control` によりターニングポイントが解禁される。
7. 成功結果と失敗結果で別のイベントが有効になる。
8. セーブ・ロード後も同じページ、同じ解禁状態になる。

## 16. 実装順

1. カタログ、状態ファイル、DAG検証
2. イベント遭遇セッションと終了時取得
3. セーブ・ロード・ニューゲーム対応
4. インラインタグ描画とクリック矩形
5. 注釈会話スタック
6. 日記の日別追記と人物別固定ページ
7. ターニングポイントUIと判定器インターフェース
8. イベント解禁サービスへの集約
9. event editorのタネ編集・検証UI

この順序なら、意味判定モデルが未確定でも、タネ取得から日記表示までを先に完成・検証できる。
